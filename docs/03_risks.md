# Реестр рисков проекта

## 1. Идентификация рисков
Мы выделили основные риски, которые могут повлиять на успех проекта. Риски разделены на категории: технические (Т), организационные (О) и риски требований (ТР).

| ID | Категория | Описание риска | Вероятность (1-5) | Влияние (1-5) | Уровень (В*В) |
|----|-----------|----------------|-------------------|---------------|---------------|
| R1 | Т | Ошибки при подключении к удаленной БД MySQL (неверные права, блокировка портов) | 4 | 5 | 20 (Высокий) |
| R2 | О | Болезнь или отсутствие одного из участников команды | 3 | 4 | 12 (Средний) |
| R3 | Т | Конфликты при слиянии веток в Git (merge conflicts) | 4 | 3 | 12 (Средний) |
| R4 | ТР | Изменение требований со стороны преподавателя (или "расползание" функционала) | 2 | 4 | 8 (Низкий) |
| R5 | Т | Ошибки в коде фронтенда при интеграции с API | 3 | 4 | 12 (Средний) |
| R6 | О | Срыв дедлайнов из-за несогласованности действий команды | 3 | 5 | 15 (Высокий) |

## 2. Качественный анализ (Матрица рисков)
На основе оценки вероятности и влияния мы построили матрицу. Риски с уровнем выше 15 требуют немедленного реагирования.

- **Высокий уровень (Красная зона):** R1, R6. Требуют разработки плана реагирования.
- **Средний уровень (Желтая зона):** R2, R3, R5. Требуют постоянного мониторинга.
- **Низкий уровень (Зеленая зона):** R4. Принимаются как допустимые.

## 3. План реагирования на риски
Для наиболее критичных рисков мы разработали стратегии реагирования:

- **R1 (Ошибки БД):** 
  - *Стратегия:* Снижение.
  - *Действия:* Проверить права доступа в панели хостинга, использовать dbForge для тестирования подключения до написания кода. Иметь резервную локальную БД (SQLite) на случай полного отказа удаленной.
- **R6 (Срыв дедлайнов):**
  - *Стратегия:* Снижение.
  - *Действия:* Использовать Kanban-доску для ежедневного контроля задач, проводить короткие митинги (15 минут) раз в 2 дня, использовать буферы времени (PERT).
- **R3 (Конфликты Git):**
  - *Стратегия:* Снижение.
  - *Действия:* Делать git pull перед началом работы, использовать feature-branches и Pull Requests (как мы и делаем), проводить код-ревью.
