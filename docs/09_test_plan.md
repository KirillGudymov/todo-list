# План тестирования ToDo List

## 1. Цель тестирования

Проверить соответствие приложения требованиям из
[05_requirements.md](05_requirements.md), выявить ошибки в основных
пользовательских сценариях и убедиться в защите данных пользователей.

Этот документ описывает планируемые проверки.
Наличие тест-кейса в таблице не означает, что он уже выполнен
или автоматизирован.

## 2. Область тестирования

Проверяются следующие функции:

- US-01: регистрация;
- US-02: авторизация;
- US-03: создание задачи;
- US-04: просмотр списка задач;
- US-05: редактирование задачи;
- US-06: изменение статуса задачи;
- US-07: удаление задачи;
- US-08: управление категориями;
- US-09: фильтрация и сортировка;
- US-10: защита данных.

## 3. Виды тестирования

### 3.1. Модульное тестирование

Проверка отдельных функций и компонентов в изоляции.

Планируемые проверки:

- валидация обязательного заголовка задачи;
- проверка минимальной длины пароля;
- логика фильтрации и сортировки, если она выделена в отдельные функции;
- отображение полей форм и сообщений об ошибках;
- обработка действий пользователя в компонентах интерфейса.

Внешние зависимости при необходимости заменяются тестовыми
заглушками.

### 3.2. Интеграционное тестирование

Проверка совместной работы API, бизнес-логики и тестовой базы данных.

Планируемые проверки:

- регистрация пользователя и сохранение его данных;
- вход и выдача JWT-токена;
- создание, чтение, редактирование и удаление задач;
- сохранение изменений статуса;
- создание и удаление категорий;
- сохранение задач при удалении категории;
- фильтрация и сортировка через API;
- запрет доступа к задачам другого пользователя.

### 3.3. UI-тестирование

Проверка интерфейса и пользовательских сценариев в браузере.

Планируемые проверки:

- наличие полей в формах регистрации и входа;
- отображение ошибок;
- переход на главную страницу после входа;
- создание и редактирование задач;
- изменение статуса в один клик;
- визуальное отличие выполненных задач;
- подтверждение и отмена удаления;
- работа категорий, фильтров и сортировки;
- перенаправление гостя на страницу входа.

Полные пользовательские сценарии в браузере на данном этапе
планируется проверять вручную. Автоматизация отдельных
UI-компонентов не заменяет проверку всего приложения.

## 4. Тестовое окружение и данные

Для выполнения проверок используются:

- запущенные frontend и backend приложения;
- отдельная тестовая база данных;
- браузер с указанием названия и версии в отчёте о проверке;
- два пользователя: A и B;
- задачи, принадлежащие каждому из пользователей;
- категории «Работа», «Учеба» и «Дом»;
- задачи с разными заголовками, дедлайнами и статусами.

Для проверки регистрации используются новые email-адреса.

Проверки изменения и удаления данных выполняются только
на тестовых данных.

## 6. Инструменты тестирования

### 6.1. pytest

Планируется использовать для тестирования backend на Python:

- модульных проверок валидации и бизнес-логики;
- интеграционных проверок API;
- проверки работы с тестовой базой данных;
- проверки авторизации и разграничения доступа.

Тестовые пользователи, задачи и категории подготавливаются
через фикстуры. Клиент для запросов к API выбирается
в соответствии с backend-фреймворком проекта.

### 6.2. Vitest

Планируется использовать для автоматических проверок frontend:

- функций обработки данных;
- логики фильтрации и сортировки, если она реализована на frontend;
- отдельных компонентов интерфейса;
- обработки действий пользователя;
- отображения состояний и ошибок.

Для компонентных проверок при необходимости подключаются
совместимые с frontend-стеком средства рендеринга компонентов
и тестовое DOM-окружение.

### 6.3. Ручная проверка в браузере

Используется для проверки полных UI-сценариев:

- регистрация и вход;
- управление задачами и категориями;
- фильтрация и сортировка;
- подтверждение удаления;
- визуальные состояния;
- переходы между страницами.

## 7. Порядок выполнения

1. Подготовить тестовое окружение и тестовые данные.
2. Выполнить модульные проверки.
3. Выполнить интеграционные проверки.
4. Пройти UI-сценарии в браузере.
5. Зафиксировать результаты и найденные дефекты.
6. После исправлений повторить неуспешные проверки
   и связанные с ними сценарии.

Для каждого выполненного тест-кейса фиксируются:

- ID;
- результат: пройден, не пройден или заблокирован;
- фактический результат при отклонении;
- ссылка на дефект, если он обнаружен.

## 8. Критерии завершения проверки приложения

- Все запланированные тест-кейсы выполнены либо имеют
  документированную причину блокировки.
- Нет открытых критических дефектов, приводящих к потере данных
  или доступу к чужим задачам.
- Остальные известные дефекты зафиксированы и согласованы
  с командой.
- Результаты проверок сохранены.

Эти критерии относятся к будущей проверке приложения.
Задача по подготовке плана не подтверждает,
что приложение уже прошло тестирование.

## 9. Вопросы для уточнения

В требованиях не определены следующие детали:

- направление сортировки по умолчанию;
- положение задач без дедлайна при сортировке;
- область уникальности названий категорий:
  в рамках пользователя или всей системы;
- точные коды HTTP-ответов при отказе в доступе к чужой задаче.

До выполнения соответствующих проверок эти детали
нужно согласовать с командой. В TC-20 пока проверяется
минимальный сценарий: дубликат категории у одного пользователя.
